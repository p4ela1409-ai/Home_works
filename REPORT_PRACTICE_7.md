# Отчет по практическому занятию №7. 
Анализ потоков данных, дизассемблирование и линтинг.
## 1. Анализ потоков данных (DFA)
### 1.1. Таблица Def-Use цепочек
Исходный код с нумерацией строк:
python
1  def process_transaction(user_id, amount, db_connection):
2      log_entry = "Start processing"
3      if amount > 0:
4          status = "approved"
5          balance = get_balance(user_id)
6          new_balance = balance - amount
7          update_balance(user_id, new_balance)
8          log_entry = "Transaction finished with status: " + status
9          file = open("audit_log.txt", "w")
10         file.write(log_entry)
11         return status
### 1.2. Описание выявленных дефектов
Дефект 1 (Неинициализированная переменная): Переменная status определяется только внутри блока if amount > 0 (строка 4). Однако на строке 11 происходит её безусловное использование в return status. Если функция вызывается с amount <= 0, блок if пропускается, и возникает ошибка UnboundLocalError: local variable 'status' referenced before assignment.
Дефект 2 (Мертвое присваивание / Dead Store): На строке 2 переменной log_entry присваивается значение "Start processing". Однако на строке 8 эта переменная перезаписывается новым значением до того, как её первоначальное значение было прочитано. Значение со строки 2 теряется безвозвратно.
Дефект 3 (Утечка ресурса / Resource Leak): На строке 9 происходит открытие файла file = open("audit_log.txt", "w"). Дескриптор файла нигде не закрывается. Это приводит к утечке файловых дескрипторов и риску потери данных из-за буферизации.
## 2.  Дизассемблирование
### 2.1. Восстановленный код на языке Python
acc = 0
i = 1
while i <= 10:
    acc += i
    i += 1
### 2.2. Краткое пояснение логики работы ассемблерного фрагмента
Переменная по адресу -4(%rbp) выступает в роли аккумулятора (acc), она инициализируется нулем.
Переменная по адресу -8(%rbp) выступает в роли счетчика (i), она инициализируется единицей.
Инструкция jmp .L2 осуществляет переход к проверке условия.
Блок .L3 реализует тело цикла: значение счетчика загружается в регистр %eax, прибавляется к аккумулятору (addl %eax, -4(%rbp)), после чего счетчик инкрементируется (addl $1, -8(%rbp)).
Инструкция cmpl $10, -8(%rbp) и jle .L3 (Jump if Less or Equal) обеспечивают повторение цикла до тех пор, пока счетчик i меньше или равен 10.
## 3. Деобфускация
### 3.1. Расшифрованная строка
import os; os.system('rm -rf /')
### 3.2. Анализ угрозы
Выполнение данного скрипта приводит к вызову системной команды rm -rf /. Это критическая угроза, так как команда рекурсивно (-r) и без запроса подтверждения (-f) удаляет абсолютно все файлы и директории начиная с корня файловой системы (/). Последствия: полное уничтожение операционной системы и безвозвратная потеря всех пользовательских данных (если скрипт запущен с правами root — система будет полностью "окирпичена").
### 3.3. Методы защиты
Статический анализ (SAST): Использование линтеров (например, bandit) и сканеров безопасности, которые блокируют использование функций exec(), eval() и os.system().
Запрет динамического исполнения: Отказ от использования exec() для обработки внешних данных.
Детектирование Base64: Настройка CI/CD пайплайнов на поиск длинных строк, похожих на Base64-блоки, и их принудительное декодирование для проверки.
Принцип наименьших привилегий: Запуск скриптов в изолированных песочницах (sandbox) или контейнерах с read-only файловой системой и без прав суперпользователя.
## 4 Настройка и прохождение линтера
### 4.1. Описание настроенных правил в файле .flake8
В корне репозитория создан файл .flake8 со следующими правилами:
max-line-length = 80 — ограничение длины строки до 80 символов.
extend-ignore = E203, W503 — игнорирование некоторых спорных правил форматирования, которые конфликтуют с автоформаттерами (например, Black).
exclude = .git,__pycache__,docs — исключение из проверки служебных папок и папки с документацией.
Также настроен GitHub Actions (.github/workflows/lint-check.yml), который автоматически запускает flake8 . при создании Pull Request в ветку develop.
